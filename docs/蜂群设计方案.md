# 基于ClaudeCode的经营智能体蜂群设计方案

- 日期：2026-09-03
- 状态：已评审（分节确认）
- 适用团队规模：5–20 人

## 1. 背景与目标

团队多人各自在本地使用千问（AI 助手），希望共同驱动一台远程服务器上的 Claude Code 开展工作，并沉淀团队能力。核心诉求：

1. 本地千问与远程 Claude Code **对等协作**：千问负责"人这一侧"，Claude Code 负责"团队这一侧"；
2. 多人同时操作**不打架**：改不同内容可并行，改相同内容有防护；
3. 服务器统一具备 **dws 等 CLI 能力**，凭证不出服务器；
4. **能力沉淀全员共享**：知识库/记忆、技能/命令、工具与账号。

## 2. 总体架构与角色分工

```
[成员A 千问]─┐
[成员B 千问]─┼──→ 【团队中转服务】──→ 【Claude Code 执行池】──→ 服务器资源
[成员C 千问]─┘    (Relay/Gateway)      (headless claude 进程)
                      │                        │
                 任务队列·路由·审计        每任务独立工作目录
                      │                        │
                 ───── 共享沉淀层 ─────────────┘
                 知识库 / 技能库 / dws等CLI(统一装服务器)
```

**分工界面**：本地千问理解人的意图、与人对话、处理本地文件；远程 Claude Code 执行所有需要共享环境、共享工具、共享知识的工作。两者之间的接口只有一个：**千问通过 CLI 命令（如 `team-agent run "任务描述"`）向中转服务提交任务，异步拿回结果**。双方互不感知对方内部实现，可独立升级换代。

> 为什么采用中转服务而非 SSH/MCP 直连：见附录 A。

## 3. 中转服务设计

**技术选型**：FastAPI（Python）+ SQLite，单进程支撑 5–20 人团队，systemd 部署。

### 3.1 核心 API（全部带用户 token 认证）

| 接口                        | 作用                                            |
| ------------------------- | --------------------------------------------- |
| `POST /tasks`             | 提交任务：任务描述 + 目标项目 + targets + 优先级，返回 `task_id` |
| `GET /tasks/{id}`         | 查询状态/结果摘要                                     |
| `GET /tasks/{id}/stream`  | SSE 实时流，千问可边执行边向用户直播进展                        |
| `POST /tasks/{id}/cancel` | 取消任务                                          |
| `GET /tasks/{id}/diff`    | 查看该任务改动了哪些文件（冲突判断依据）                          |

### 3.2 会话模型

每个任务启动独立的 `claude -p`（无头模式）进程，session_id 入库：

- 任务之间上下文天然隔离、互不污染；
- 支持 `claude --resume` 续接——对结果不满意时，提交"追任务"挂到原 session 继续改，无需从头再来。

### 3.3 并发控制

- 执行池上限 3–4 个并行 Claude 进程（受 API 限额与服务器 CPU 约束），多余任务排队；
- 优先级两档：普通任务 FIFO；`urgent` 插队；
- 每任务默认 30 分钟超时，防僵尸进程。

### 3.4 任务生命周期

`queued → running → review（待检查）→ done / conflict / failed`

## 4. 并行不打架的机制（无 git 版）

原则：**改不同内容可以并行**——乐观并发，事前防碰 + 事后兜底。

### 4.1 每任务独立工作目录（并行的物理基础）

- `/workspace/tasks/<task_id>/` —— 任务临时工作区，Claude Code 的 cwd；10 个任务并行互不可见；
- `/workspace/users/<成员名>/` —— 成员个人持久区；
- `/workspace/shared/` —— 共享区（知识库、团队产出），唯一可能"打架"的地方，重点管控。

### 4.2 任务提交时声明目标（事前防碰）

千问提交任务时携带 `targets` 字段（要动哪些目录/文件，如 `["shared/reports/9月/"]`）。中转服务比对在途任务声明：

- 不重叠 → 直接并行放行；
- 重叠 → 返回提示"⚠️ 李四的任务 #98 正在动 `shared/reports/`，确认继续或排队等待"，由人决定。

管不住手但管得住入口——绝大多数冲突在提交前被错开。

### 4.3 完成时变更扫描（事后兜底）

任务结束，服务扫描共享区，把本任务时间窗内新建/修改的文件记入任务日志。若同一文件被两个任务的时间窗交叉修改：

- 自动保留带时间戳的副本（`report.md.bak-张三-1430`），绝不静默覆盖；
- 结果中标红提醒人工核查。

### 4.4 结果回传

千问拿到的响应 = 执行结果 + 变更文件清单 + 冲突提示（如有），信息完整可追溯。

> 升级路径：若未来团队转向大量改代码，可按项目单独引入 git worktree 方案平滑升级，不影响现有架构。

## 5. 三大共享沉淀的落地方式

### 5.1 共享知识库 → `/workspace/shared/knowledge/`

- 按主题分目录：业务知识 / 经验复盘 / 常用模板 / 数据源说明；
- 每个工作区根部放 `AGENTS.md`，写明"动手前先查 knowledge 目录"；
- 沉淀机制：千问下发任务时结尾约定"产生的可复用经验写入知识库对应目录"，团队能力随任务自然增长；
- 每周由值日生（或定时 Claude 任务）去重整理。

### 5.2 共享技能 → 模板化 HOME

- 技能集中存放 `/opt/team/skills/`，一人沉淀、全员生效；
- 中转服务为每个任务生成独立 HOME：从模板复制，其中 `.claude/skills`、`.claude/commands`、`.claude/agents` 软链到共享技能库——技能全员共享，会话记录各自隔离（支撑 `--resume`）；
- 成员贡献新技能 = 往共享目录加一个文件，下一个任务全 team 可用。

### 5.3 共享工具与账号 → 服务器统一装、统一配

- dws 等 CLI 由管理员在服务器安装一次；
- token/密钥统一放在 `/etc/team/`，权限收紧（仅服务账户可读），**凭证不出服务器**——本地千问与成员全程接触不到密钥，离职吊销即回收；
- 在 `AGENTS.md` 登记"可用 CLI 清单 + 用法示例"；为 dws 等高频工具各写一个薄 skill（封装发消息、查表格、读文档等常用操作），Claude 按需调用。

## 6. 权限与安全（最小够用）

- **成员认证**：每人一个 API token，所有任务可追溯"谁让干的"，离职吊销 token 即回收全部权限；
- **执行权限白名单**：dws、文件读写等常规操作自动放行；`rm -rf`、关机、改防火墙等高危命令拦截，任务挂起为"待人工批准"，确认后续跑；
- **网络面**：中转服务只监听内网或 Tailscale 虚拟网卡 + token 校验，不暴露公网；
- **审计**：任务级日志全量入库（谁/何时/什么任务/结果/动了哪些文件），碰凭证类工具的调用单独记明细。

## 7. 落地步骤（小步快跑，每步可停下来用）

| 阶段  | 周期      | 内容                                                 | 验收标准                                |
| --- | ------- | -------------------------------------------------- | ----------------------------------- |
| 0   | 0.5–1 天 | 服务器装 Node/Python/Claude Code/dws，配好凭证              | 单人 SSH 跑通 `claude -p` 和 `dws` 各一条命令 |
| 1   | 2–3 天   | 中转服务 MVP：提交/查询/取消 + token 认证                       | 3 名成员从本地千问各跑通 1 个真实任务               |
| 2   | 2–3 天   | 并行机制：任务目录隔离 + targets 声明 + 重叠预警 + 完成扫描             | 两人同时操作共享区不丢数据、有预警                   |
| 3   | 持续      | 沉淀层：knowledge 目录 + AGENTS.md + 共享 skills + dws 薄封装 | 新成员半天上手，技能一人沉淀全员可用                  |
| 4   | 按需      | 加固：审批流 / 审计报表 / 监控 / 备份                            | 视团队规模再启动                            |

## 附录 A. 为什么是中转服务而不是 SSH/MCP 直连

| 维度    | 中转服务（本方案）                      | SSH + 无头模式    | MCP 协议直连    |
| ----- | ------------------------------ | ------------- | ----------- |
| 多人并发  | 队列模型，多对多可管可控                   | 会话互相踩踏，需自行拼脚本 | 服务端能力有限，无队列 |
| 冲突防护  | targets 声明 + 重叠预警 + 完成扫描，挂在服务上 | 几乎做不了         | 做不了         |
| 权限与审计 | 按人 token + 白名单 + 全量日志          | 依赖服务器账号，粒度粗   | 粒度粗         |
| 客户端成本 | 千问只需会调一条 CLI                   | 每人配 SSH 密钥    | 需等 MCP 生态成熟 |
| 开发量   | 一个几百行 FastAPI 服务               | 零开发           | 低，但能力天花板也低  |

结论：SSH 直连在多人并发时会话互相踩踏；MCP 直连做不了任务队列和按人隔离。中转服务把"多对多"（多成员 × 多 Claude 进程）变成可管可控的队列模型，也是防冲突和审计的挂载点。
